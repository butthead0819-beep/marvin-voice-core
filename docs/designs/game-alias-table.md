## Problem Statement

大家用英文講遊戲名，但語音辨識常把英文聽成中文糊字，查詢就跟著失敗。近 30 天 118 筆查詢裡，Grounded 2 被聽成：

- Grandetwo、Gronde 2、Grounde too、Grandy two、Brotoo、幫註
- 圓地豆、光點兔、光烈兔、光點二代
- 韋小說、圍剿世界生存戰二、我想生存上 N 3D2

**最嚴重的一筆**：10/22 12:14「你知道幫註那種戲嗎」，查詢模型很有自信地答成 Brotato。但這群人根本沒玩 Brotato，那是 Grounded 2（使用者 10/23 更正）。另外，10/21 15:33–15:43 那一串因為沒認出遊戲名，都是空答或「找不到」。

舊的遊戲術語工具（LLM 憑記憶生成的字典）已經刪掉了（分支 `chore/remove-game-dict`），要換成以真實資料為準的版本。

## What Makes This Cool

Marvin 會知道「這群人在玩什麼」。聽起來像遊戲名的糊字，它會先往大家真的在玩的遊戲對，不會去網路上隨便猜一款。這張表的資料全部來自你們講過、被聽錯過的真實句子，不是模型想像出來的。

## Constraints

- 零 LLM、零付費：比對是本地查表（[[feedback_paid_calls_must_record]] 的帳本快滿了）。
- 誤聽說法只能從真實 STT／查詢 log 挖，不准讓 LLM 生成（舊術語表就是死在這裡）。
- STT 層的辨識提示屬於語音骨幹。動到它要先讀 `build_stt_context` 和各 STT 引擎怎麼用 prompt，所以放到最後一步，可以單獨關掉。

## Premises（10/23 使用者確認）

1. 名詞分兩層：遊戲名＝英文原名；遊戲內名詞（地區、生物、道具）＝PS 版官方繁中。第一版只做遊戲名這一層。
2. 誤聽說法一律從 log 挖，你確認過才收進表。
3. 第一版不要求每個詞附出處網址（量小，太重）。之後擴大到遊戲內名詞時再決定。
4. 先量今天部署的 `recent_games`＋問題整理的效果，再決定 wiki 要做多大。

## Approaches Considered

- **A 遊戲名誤聽對照表**（採用）：見下方。
- **B 兩層 wiki**（遊戲內名詞＋標哪一代）：暫緩。還不知道搜尋自己救不回來的遊戲內名詞有多少，等 A 上線後量了再說。
- **C 收割模型的更正句當候選**：暫緩，之後當成 A 的成長機制。單獨做沒有地方放，而且模型自己也會猜錯（Brotato 就是例子）。

## Recommended Approach：A

### 資料

一個進版控的 JSON 檔，路徑在 eng review 定。格式：

```json
{"games": [
  {"name": "Grounded 2",
   "zh": "微小世界生存戰2",
   "aka": ["禁閉求生2"],
   "heard": ["Grandetwo", "Gronde 2", "Grounde too", "Grandy two", "Brotoo", "幫註",
             "圓地豆", "光點兔", "光烈兔", "光點二代", "韋小說", "圍剿世界生存戰二"],
   "series": "Grounded"}
]}
```

- `heard`：只收你確認過的誤聽說法。
- `zh`／`aka`：官方中文名和別稱。查詢答案裡出現過「微小世界生存戰2」「禁閉求生」，可以拿來當同義詞。

### 初稿怎麼來

寫一支一次性腳本掃 `records/ambient_qa.jsonl` 和 `records/daily/stt_*.log`，挑出以下兩種句子當候選：

- 答案或下一句提到表內遊戲，但原句沒有出現正式名稱
- 前後 60 秒內同一個人又講了正式名稱

候選列給你勾，勾過的才寫進 `heard`。

### 比對

純函式。原句先正規化（casefold、去空白、去標點），再對 `heard`／`zh`／`aka` 做子字串比對。命中就回傳那款遊戲。第一版不做拼音模糊比對，先看精確比對的覆蓋率夠不夠。

### 怎麼用

- **命中**：在問題整理和查詢的 prompt 加一段強提示，例如「【聽到的「圓地豆」＝遊戲 Grounded 2（微小世界生存戰2）】」。這段跟現在的軟性遊戲提示（`_GAME_HINT_LABEL`）分開。
- **沒命中**：`recent_games` 的軟性提示**照舊**。這一版只改一個變數，才量得出效果。「不再無條件塞遊戲名」等量完再決定。
- **STT 辨識提示**（最後一步、可單獨關）：`recent_games` 有值的時候，把正式遊戲名稱放進 `router.game_dict_string`，讓 `build_stt_context` 在源頭就提示 STT。要先確認哪些 STT 引擎真的會吃這個 prompt。

## Open Questions

1. JSON 檔要放哪：repo 根目錄，還是 `config/`？
2. STT 提示在現行主力 STT 引擎上到底有沒有作用？這一步做不做，取決於確認的結果。
3. 命中但大家其實在講一代的時候怎麼辦？例如問「一代的綠背椿象在哪」。第一版只標遊戲系列，不管版本。版本問題要等 B 的「哪一代」欄位。
4. 誤聽說法如果撞到日常用語（例如「幫註」會不會出現在非遊戲句子裡）怎麼處理？要用全部 log 跑一次誤命中率。

## Success Criteria

- **回放**：10/21–10/22 跟遊戲有關的查詢（約 20 筆），**用更正過的標準答案**（「幫註」＝Grounded 2）。全部比對到 Grounded 2，Brotato 那題不再答錯。
- **誤命中**：近 30 天的非遊戲查詢加上一般 STT 句子，誤命中 0 筆。
- **上線一週**：跟遊戲有關的查詢裡，空答、「找不到」、答成別款遊戲的筆數。跟 10/21–10/22 的基準比（那段時間約 5 筆空答或「找不到」，加 1 筆答成 Brotato）。

## Distribution Plan

沿用現有的部署流程：PR → CI（workflow CI）綠 → merge → 重啟 bot。重啟避開 20–24 點。

## Dependencies

- **要先修 13 題評估的標準答案**：「幫註」那題的正確答案是 Grounded 2，不是 Brotato。順便用正確答案重評問題整理的思考檔位，調低思考的版本當初答對了卻被否決，可望把 6s 降到約 1.3s。
- 清理分支 `chore/remove-game-dict` 先 merge，免得改到同一個檔案。

## Next Steps

1. 修正 13 題評估的標準答案，重評問題整理的思考檔位。
2. 寫挖誤聽候選的一次性腳本，產出候選清單給你勾。
3. 對照表 JSON＋比對純函式＋測試，含誤命中回放。
4. 接進問題整理和查詢的 prompt（命中時才加強提示）。
5. 上線量一週，再決定要不要做 STT 提示，以及 B 和 C。

## What I noticed about how you think

- 我把「幫註」當成 Brotato 寫進前提，你直接說「沒有 Brotato，這個是錯的」。這一句推翻了一個評估的標準答案和一個延遲決策。最懂資料對不對的是在場玩的人。
- 你四個願望全選，但第一版選了最小的 A，也同意「先量再決定大小」。想要的很多，下手只先切一刀。
- 你否決「每詞附出處」的理由是「太重，第一版不需要」。規矩要配合現在的規模，不是一開始就把規矩訂滿。
