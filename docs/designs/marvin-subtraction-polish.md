## Problem Statement

固定使用者目前還算滿意。使用者的方向是**先做減法，把現有功能做到極致**。

定位（前一輪已定案）：Marvin 是這群朋友聊天房的電台主持人。歌負責情緒，歌與歌之間的空檔是它的舞台。

近 30 天資料指出兩個問題：DJ 最基本的動作還不穩；Marvin 的嘴巴會暴衝，而且講來講去都是同一套。

## 證據（近 30 天，已排除 test speaker）

資料來源都是會長期保存的 jsonl（`records/`）。`bot_stdout.log` 只保留不到一天，不當驗收依據。

**DJ 基本功**

- **frustration 共 6 次**（`judge_outcomes.jsonl`，`winner_name == 'frustration'`），逐筆歸屬如下：

| 日期 | 講者 | raw_query | 歸屬 |
|---|---|---|---|
| 09-03 23:53 | showay | 播放《總會有人》 | 正常點歌卻被判成 frustration → 項目 2 的「frustration 誤判」一起查 |
| 09-08 18:04 | showay | 重覆播放這首 | 想重播 → 項目 2 |
| 09-08 18:05 | showay | repeat 這首 | 想重播 → 項目 2 |
| 09-18 19:01 | showay | 一個半小時的不是馬文後背 | 語意不明，**不在本輪範圍** |
| 09-23 09:33 | 狗與露 | …播放淳華的…播放陳華的如果… | 歌手名聽錯（陳綺貞）→ 項目 3 |
| 09-24 15:16 | showay | …帕拉梅拉不是這首歌… | 播錯歌 → 項目 3 |

- **沒有「重播這首」的功能**：`personal_shuffle_agent` 的 `_LOOP_WORDS` 雖然含「重複／循環」，但一定要搭配「我的歌單」這類字才會觸發。
- **不喊喚醒詞問歌名：回應率未量測**（eng review S2：nowake 分派從不寫 `judge_outcomes.jsonl`，見 [intent_bus.py:259](../../intent_bus.py)）。`pipeline_timing.jsonl` 裡 route 為 `nowake_bus` 的 6 筆：

| 時間 | 講者 | 文字 |
|---|---|---|
| 09-01 00:34:19 | 大肚 | 但是歌名是什麼 |
| 09-09 20:47:07 | 大肚 | 現在這是什麼歌啊 |
| 09-13 15:13:53 | showay | 這是什麼歌 |
| 09-13 15:14:18 | showay | 我剛隻說這是什麼歌 |
| 09-13 15:14:30 | showay | 沒有對可是我剛剛在問你這是什麼歌的時候他就回覆了他沒有… |
| 09-13 15:15:12 | showay | 這是什麼歌 |

  這 6 筆都經過 [cogs/voice_controller.py:1933](../../cogs/voice_controller.py) 的 `_is_music_info` 分支**進了 intent bus**，但 `judge_outcomes.jsonl` 裡對應時間沒有任何 now_playing 勝出。30 天內 now_playing 唯一一次勝出是 09-09 20:47:14 狗與露說「馬文這首是什麼歌」（有喊喚醒詞，而且就在大肚沒得到回答的 7 秒後）。根因還不知道（當天的 log 已被輪替掉）。
  計算方式：分子 = 這些 nowake 問句在 60 秒內有 now_playing 勝出、而且 TTS 真的播出的筆數；分母 = `nowake_bus` 裡符合問歌名句型的筆數。

- **延遲**：主路徑（`main_bus`，n=154）總計 p50 2476ms、p90 3864ms：

| 階段 | p50 | p90 |
|---|---:|---:|
| stt_start → stt_done | 258 | 487 |
| **stt_done → dequeued** | **1029** | **1946** |
| question_done → cleaner_done | 1038 | 1527 |
| cleaner_done → intent_dispatched | 1 | 3 |

  `stt_done → dequeued` 在 per-speaker 平行化（`speaker_dispatch.py`，7/3 上線）之後，常態日 median 是 **400–500ms**（見記憶 `stt_queue_tail_single_worker`，7/7–7/14 資料）。現在 p50 是 1029ms，約兩倍，**可能是回歸**。這個表格不包含分派之後的搜尋和播放時間。

**嘴巴**

- **冷場開話題沒人理**：ProactiveTopicAgent（idle_tick）187 次，只有 29% 之後有人接話（`speak_outcomes.jsonl` 的 `had_followup_stt`，這是弱訊號）。Bridge 和 MemoryCallback 則是 86–93%。
- **暴衝**：主動發話每個活躍小時 p50=2、p75=4、p90=7；但 9/1 13 點達 68 次（Bridge 43、ProactiveTopic 24），9/16 23 點 ProactiveTopic 單獨 34 次。
- **厭世詞重複（線索，不當基準）**：`response_feedback.jsonl` 近 30 天 14 則中有 9 則含「無意義／宇宙／運算資源／處理器」；5 則「嚴重：20 秒內無反應」全部是厭世句。這批是被標記過回饋的回應，樣本有偏誤，所以只當作線索，真正的基準在項目 5 裡重新量。[marvin_prompts.py:93](../../marvin_prompts.py) 把「宇宙虛無感」設成預設底色。

## Premises（已同意；第 1 條依審查修正措辭）

1. **這一輪只補「已經觀察到有人卡住」的缺口，不做沒有證據的新功能。** 本輪允許的新行為只有兩個：點歌低信心確認（項目 3）、開口預算（項目 7）；重播（項目 2）經 eng review 確認是既有 `ReplayAgent` 補關鍵字，不是新行為，因為它們各自對應到上面的 frustration 或暴衝證據。「單曲循環」沒有人要求過，**這輪不做**。「看場合音效」擱置。
2. **DJ 的極致 = 基本動作零失誤**：點歌一次就對、問歌名一定有回答、「重播這首」能用、等待時間更短。
3. **嘴巴的極致 = 每次開口都值得聽。厭世是 Marvin 的靈魂，要保留；要改的是「重複」和「暴衝」。**
4. **每一項都能單獨回滾**：每一項都有自己的 env flag（見各項），關掉就是原本的行為。一週後資料顯示沒人想念被降權的東西，才真的清 code。
5. **驗收看 frustration 和「沒人理」的比例有沒有下降**，不看新功能的使用量。

## Approaches Considered

- **A 補洞 + 降權**：只做 1、2、5、6。未採用，因為使用者要把點歌聽錯（最大宗的 frustration）一起處理。
- **B 全面打磨（採用）**：下面全部 7 項。
- **C 靜音一週**：否決，因為會把接話率 86–93% 的 Bridge、MemoryCallback 一起砍掉。

## 共通規則（7 項都適用）

- **發包**：照 CLAUDE.md 發包給 sonnet（`claude -p --model sonnet --permission-mode acceptEdits`）。發包前我要先讀完相關原始碼、查完該項的「待查」，任務檔寫到沒有發揮空間，並寫明「有疑問就停下來回報」。
- **收回來驗收**：`cat` 測試檔確認沒有把被測邏輯複製進測試；`git diff` 逐行看；自己用 `venv_simon` 跑測試；沒走 TDD 的改動要做 mutation check。
- **LLM 呼叫**：一律走 LLM bus；付費呼叫一定要記帳（`llm_paid_usage.jsonl`）。
- **錯開上線**：一次只 land 一項，每一項至少觀察 **3 個有人在線的日子**才 land 下一項，這樣效果才能分別歸因到各項。
- **重啟**：晚上 8 點到 12 點不重啟。
- **frustration 計數的公平性**：前後比較一律用**本輪開工前那個 commit** 的 frustration 判斷邏輯，對前後兩段資料重新打分；同時人工讀一遍所有「點歌、重播、問歌名」附近的句子。避免項目 2 修好之後，那兩句只是換了標籤、數字卻看起來變好。

## 規格：7 個工作項目

### 1. 不喊喚醒詞問歌名，一定要有回答
- **Flag**：`MARVIN_NOWAKE_NOWPLAYING=1`（預設開；`0` = 原本行為）
- **先看得見（eng review D4）**：新增 `records/nowake_outcomes.jsonl`，intent bus 收到 `dispatch_source=="nowake"` 時寫一筆（ts、speaker、raw_text、winner name／confidence、各 agent 的 gate 拒絕原因），比照 judge_outcomes 的 pytest 防污染規則；`judge_outcomes.jsonl` 不動。這份紀錄跟項目 1 的第一個 PR 一起上線。
- **待查（/investigate）**：上面那 6 句進了 bus 之後，死在哪一層。注意 `NowPlayingAgent` 的 `r"這(?:是)?什麼(?:歌|曲)"` 本來就吃得到「這是什麼歌」。依序排查：NowPlayingAgent 的句型沒吃到 → nowake 模式被 judge 或 guard 擋掉 → 有勝出但回應被 play_tts guard 吃掉（參考 `join_greeting_playtts_guard_stack`）。**先在 now_playing 路徑補一行結構化 log**（進入、判斷結果、TTS 有沒有真的推出去），寫進 `records/now_playing_outcomes.jsonl`。
- **離線重現不出來的話**：先只 land 那行 log，上線觀察到下一次失敗，拿到證據再修。
- **行為**：

| 情境 | 回應 |
|---|---|
| 正在放歌，不喊喚醒詞問歌名 | 用語音回答歌名和歌手 |
| 沒在放歌 | 不回應 |
| 在放歌，但拿不到歌曲資訊 | 回「這首我也不確定」之類的一句 |
| DJ 口白或其他 TTS 正在講 | 排在後面講，不打斷 |
| 30 秒內同一首又被問 | 只回答一次 |

- **驗收**：
  - 上面 6 句真實語料全部路由到 now_playing，**而且 TTS 真的推進 mixer**（測試要驗到 push，不能只驗 handler 回傳文字）。
  - 反例：/investigate 從近 30 天 STT 逐字稿裡挑出 10 句含「歌」字的一般聊天（例如「這首歌好好聽」），寫進測試 fixture，全部**不能**觸發。
  - 上線後，`now_playing_outcomes.jsonl` 的問歌名有回應比例 ≥ 90%。

### 2. 重播這首 ＋ frustration 誤判（eng review D3 修訂）
- **Flag**：不需要（只擴充既有 regex；回滾＝revert PR）
- **行為**：沿用既有 `ReplayAgent`（[intent_agents/replay_agent.py](../../intent_agents/replay_agent.py)）「立刻從頭播」的行為，只擴充 patterns，涵蓋「重覆播放這首／重複播放這首」與「repeat 這首」。新 regex 必須錨定「這(一)?首」並排除「我的」，避免跟 `personal_shuffle` 弱訊號（同為 0.90）平手。不新增 agent、不改去重與 prefetch。
- **待查**：9/8 兩句和 9/3「播放《總會有人》」為什麼會被 frustration 搶走（regex 還是信心值）。
- **驗收**：
  - 9/8 兩句路由到 `ReplayAgent`，**不產生** frustration outcome；「重複播放我的歌（單）」仍路由到 `personal_shuffle`。
  - 9/3 那句路由到一般點歌，不產生 frustration outcome。
  - 真正的抱怨句（從 `frustration_agent.py` 既有的測試案例取）仍然路由到 frustration。
  - `personal_shuffle` 的既有測試全部維持綠燈。

### 3. 點歌聽錯的救援：歌手名校正 → 低信心確認
- **Flag**：`MARVIN_MUSIC_RESCUE=off|correct_only|confirm`（預設先 `correct_only`，確認對話等校準通過才切 `confirm`）
- **效能**：已知歌手的拼音在載入時算好快取（比照 `MusicFastpath` 索引），不在每次點歌時重算。
- **相似度**：校準和 runtime 一律先用 `song_name_clean` 清掉標題雜訊（MV、官方、【】等），再用同一個函式算拼音相似度。沿用點歌拼音 fastpath 的做法，**不疊 rapidfuzz**（見 `dj_joke_bank_pinyin_match`）。
- **3a 歌手名校正**：STT 文字裡的歌手名，跟 `music_memory` 已知歌手做拼音相似度比對（例如「陳華／淳華」→「陳綺貞」）。只有在「原文不是任何已知歌手」而且「最佳候選分數 ≥ 門檻、並且比第二名高出至少一個差距」時才校正。
- **3b 低信心確認**：搜尋結果和 query 的相似度低於門檻時，不直接播，先問「你是說 {歌手} 的〈{歌名}〉嗎？」。
  - **實作方式（eng review D2/A2/D6）**：做成 `wake_followup` 的新 pending type `music_confirm`，沿用 `_pending_followups` 每人追問窗口（窗口依 type 設定，這個 type 為 15 秒），pending 存 resolved info，確認時直接播那首、不重搜。
  - 問句用 protected TTS 講出來（排在點歌 ack、DJ 口白後面），同時貼文字；**窗口從問句推進 mixer 的時間開始計時**；TTS 失敗就退回只貼文字、從貼文字的時間起算。
  - 確認窗口 15 秒；**只有原本點歌的人**的回應才算，其他人完全不受影響；不需要喊喚醒詞。
  - 先判否定、再判肯定（`_AFFIRMATIVE_WORDS` 含「播／播放」，「不是，播 XX」不能被當成確認）；窗口內的否定句由確認流程接走，不再觸發 FrustrationAgent 回話。
  - 整句等於白名單詞（對、對啊、是、是的、嗯、沒錯、好、好啊、好的、可以、要、播吧、點吧；去掉空白、標點與「馬文」前綴後比對）→ 播 pending 裡的那首（第二輪 eng D1）。判斷順序：否定 → 整句白名單 → 新點歌（作廢舊確認，CEO-3）→ 放行。
  - 回「不是」加上歌名（例如「不是，是 XX」）→ 用新的歌名重新點歌。
  - 單獨回「不是／不要」→ 取消。
  - 其他任何話 → `match_followup` 回 None、**原封不動走原本的路徑**（不改寫、不吞掉），pending 保留到逾時。不會把閒聊當成點歌。
  - 逾時 → 取消，不播，只記 log，不講話。
  - 確認窗口期間，bus 照常處理其他人的指令。
  - 已知風險：原點歌者剛好隨口說了「嗯」會被當成確認。影響是播出 Marvin 本來就打算播的那首，所以可以接受。
- **校準（發包前一定要做）**：近 30 天的點歌紀錄，把成功的和上面 9/23、9/24 那兩筆分開，各算一次分數。
  - 3a：歌手名校正**不能改到**任何一筆原本成功的點歌（0 筆），而且要改對 9/23 那筆。
  - 3b：如果門檻可以做到「成功點歌觸發確認 ≤ 10%，並且 9/24 會觸發確認」，就啟用 `confirm`；做不到就停在 `correct_only`，只做歌手名校正。
- **驗收**：上述校準數字寫進 PR 描述；9/23、9/24 語料的測試；確認對話每一個分支（確認、改點、取消、忽略閒聊、逾時、非原點歌者）各一個測試。

### 4. 延遲：查 stt_done → dequeued 的回歸
- **Flag**：看修法而定；如果是改參數，就用 env 控制。
- **待查（/investigate）**：用 `pipeline_timing.jsonl` 的逐筆資料，按日畫出 `stt_done → dequeued` 的 median，找出從 400–500ms 變成 ~1000ms 的那一天，再對照那段時間的 commit。**不要用推測的**（見 `feedback_data_driven_diagnosis`）。也要確認量測點的位置有沒有改過。
- **行為**：是回歸就修掉；是必要的等待（例如確認流程），就寫成書面結論並關閉這一項。**不碰 cleaner**：cleaner 已經在 regex race 裡平行跑了。
- **範圍**：這段排隊是在 Discord 的 `voice_controller` → `speaker_dispatch` 路徑上。如果修到的是共用骨幹模組，就要在 PR 裡寫明，並把 satellite 路徑的測試一起跑。
- **驗收**：`stt_done → dequeued` 的 p50 回到 ≤ 500ms（歷史常態值）；或者一份書面結論，說明回升的原因和為什麼不能降。

### 5. 厭世詞彙冷卻
- **Flag**：`MARVIN_PERSONA_PHRASE_COOLDOWN=1`
- **行為**：保留厭世人格。「宇宙虛無感」從「預設底色」改成「偶爾出現的調味」（修改 [marvin_prompts.py](../../marvin_prompts.py) 第 93、108 行附近的描述）。另外維護一份「最近用過的招牌詞」清單，注入 prompt：「這幾個詞最近用過了，這次換個說法」。
  - **範圍**：只管聊天回應和主動發話（經過 `marvin_prompts` 產生的 Marvin 回應）。**DJ 口白、進場招呼、送客不在範圍內**，因為 DJ 口白常含歌名，歌名裡的「宇宙」不該被算進去。
  - **詞表**：無意義、毫無意義、宇宙、運算資源、處理器、熵、演算法。
  - **比對**：只比對 Marvin 自己產生的回應文字，子字串比對。
  - **清單**：最近 8 則回應（N=8），全頻道共用一份，`marvin_prompts` 模組層 deque，存在記憶體裡，重啟就清空（可以接受）。
  - **讀寫點（任務檔要寫死）**：組 prompt 時讀（注入點在 `gemini_router_content.py` 約 485 行的 prompt 組裝附近），拿到最終回應文字後才寫入，避免只注入不記錄。實作前先讀 router 確認最終文字的出口。
- **驗收（離線）**：
  - 從近 30 天 STT 逐字稿挑 20 個真實的聊天輸入，固定下來當測試集。
  - 改之前和改之後各跑一次，每個輸入各生成 3 次（總共 120 次呼叫），走 LLM bus 的免費池。
  - 改之前的招牌詞比例是基準；改之後要**降到基準的一半以下**。
  - 我自己讀一遍改之後的輸出，確認還是 Marvin 的口吻，而且沒有換成別的詞一直重複。

### 6. 冷場開話題降權
- **Flag**：`MARVIN_PROACTIVE_TOPIC_MODE=on|reduced|off`（預設 `reduced`）
- **行為（reduced）**：
  - 靜默門檻加倍。現在是 controller 依情況動態設 240／300／600 秒（`proactive_silence_threshold`，[proactive_topic_agent.py:84](../../proactive_topic_agent.py)），reduced 模式變成 480／600／1200 秒。
  - 在場人數 < 2 時不開話題。在場人數的來源和 `speak_outcomes` 的 `present_speakers` 相同（語音頻道裡的真人，排除 bot 和 test speaker）。
- **待查**：9/16 23 點 ProactiveTopic 34 次的暴衝是怎麼發生的（例如沒人在場卻一直觸發）。是 bug 就一起修。
- **驗收**：
  - 單元測試涵蓋三個模式的門檻，以及在場人數 < 2 時不觸發。

### 7. SpeakBus 每小時開口預算
- **Flag**：`MARVIN_SPEAK_HOURLY_BUDGET`（整數，`0` = 關閉；預設 10）
- **待查（先做）**：9/1 13 點 Bridge 43 次是正常反應（大家聊很熱）還是重複觸發的 bug。**是 bug 就先修 bug**，不能用預算把它蓋掉。
- **行為**：在 `SpeakBus.tick`（[speak_bus.py:131](../../speak_bus.py)）維護一個滾動一小時的計數。
  - **什麼時候算一次**：`tick` 回傳勝出的 bid 就算一次，不管之後 handler 有沒有真的講出來。預算管的是「決定要開口」的次數；被 guard 吃掉的另外查。
