## Problem Statement

DJ 串場口白的「這輪講哪種、怎麼講」散在 5 個地方：`dj_topic_selector`（MODE_WEIGHTS / TOPIC_MODES / select_mode）、`dj_narration_orchestrator.select_narration_mode`、`cogs/music_cog_dj_lyrics._fetch_dj_interjection_raw` 的 mode→ctx if/elif、`cogs/music_cog._DJ_MODE_TO_TTS_EMOTION`、各素材模組。`_fetch_dj_interjection_raw` 單一 method 489 行 / 319 statement，包辦素材收集、mode 決策、prompt 組裝、文字來源 cascade、TTS。

2026-10-08 加 `activity` mode 實測要動 5 個檔，而且呼叫端接線（vc 成員 → 扭蛋池）原本沒有測試覆蓋，是 mutation check 才抓到。`dj_narration_orchestrator.py` 是 Phase A 文件化，docstring 自承「沒有任何呼叫點」。

**範圍只解可維護性**（使用者確認的前提 1）：口白品質（編造、太長）不在這次範圍——已知編造根因是 LLM 路由選中 ministral-8b，與結構無關。

## What Makes This Cool

加一種新素材（今天的 Discord 動態、之後可能的天氣/行事曆/遊戲成就）從「改 5 個檔 + 祈禱接線沒漏」變成「寫一筆 mode 資料」。「Marvin 這輪為什麼講這句」讀一張表就知道，不用讀 489 行。為之後讓 Marvin 依大家反應自己調偏好（方案 C）鋪路。

## Constraints

- `cogs/music_cog.py` 有 AST size budget（只准降），新邏輯放 mixin / 純函式模組。
- 冷卻/副作用時序要保留：`select_mode` 只在**抽中**時 `mark_used`；conversation 抽中時同步重查並 `mark_consumed`（中間不能 await，PR #102 review）；callback 抽中要 `consume_callback`；memory_match 命中時**不能**呼叫 select_mode（否則白燒 life/interest 冷卻）。
- 文字來源 cascade（joke_bank → quick 模板 → LLM → autopilot 模板 → 保底報幕）與 TTS **不碰**（IO 重、風險高）。
- PR 節奏：一天 ≤1-2 個 PR（停權後承諾）；DJ 觀察週後動工。
- 新頂層模組用 `getLogger(__name__)` 的 INFO log 會被 root WARNING 吞，需在 `main_discord.setup_early_logging` 放行（已知 pitfall）。

## Premises（使用者 2026-10-08 確認）

1. 只解「加/改 mode 要動 5 處」的可維護性，不改口白品質；結構變動與行為變動分開。
2. 註冊表要同時管**優先序鏈**與**扭蛋池**——9/30 後 1245 筆口白中，revival 29%、memory_match 14%、reason 14%、song 12% 都不是扭蛋抽出來的（合計 69%），只做扭蛋池等於做一半。
3. 「用數據砍 mode」要先補反應訊號；現在只有次數。atmosphere(8)/guide(10) 少是因為進池條件嚴，不代表不受歡迎。先補「口白後 30 秒內是否被 skip」，累積一週再砍。
   - 已知雜訊：口白在**下一首開頭**疊播，skip 會混到「不喜歡這首歌」。比較時要對照同一首歌無口白時的 skip 率，或只看 mode 間相對差異。

## 現況：實際決策順序（從程式碼核對）

```
_fetch_dj_interjection_raw
  │
  ├─ revival_lines 非空 ───────────────────────────────► revival        （強制層 1）
  └─ select_narration_mode
       ├─ memory_evidence 未冷卻且未被 exclude ─────────► memory_match   （強制層 2）
       ├─ focus == "song"（autopilot 少播歌）──────────► song           （強制層 3，之後 pick_song_facet）
       └─ select_mode 扭蛋池
            候選：life(主角在場) / interest / emotional_highlight / news(2h 冷卻)
                  / callback / activity / guide(has_guide 且 focus!=topic)
                  / conversation / prev_song(⚠ 死碼) / atmosphere / quick
            規則：權重≤0 移出 → exclude_modes → 不連抽上次 → 有別的就移出 quick → 加權抽
            └─ 抽中 quick/atmosphere 且有 autopilot_reason ──► reason   （覆蓋層）
  └─ conversation 抽中但素材被另一首搶光 ───────────────► quick         （降級）
```

⚠ `prev_song`：沒有任何呼叫端傳 `has_prev_song=True`，9/30 後 0 筆，**死碼，第一刀直接刪**。

9/30–10/8 分布（1245 筆）：revival 366、memory_match 173、reason 172、song 152、life 118、conversation 80、quick 50、news 32、interest 30、emotional_highlight 30、callback 23、guide 10、atmosphere 8、activity 1、prev_song 0。

## Approaches Considered

### Approach A：只把 prompt 那半邊做成表
mode → {prompt 段落, 開場鉤子, TTS 情緒, 權重} 一張 dict；優先序鏈照舊在程式碼。S/低風險。**否決**：違反前提 2，69% 的決策仍散著。

### Approach B：完整註冊表 + 規劃器（選定；除 TopicCooldownStore 外無 IO）
見下節。

### Approach C：B + 依 skip 自動調權重（多臂吃角子老虎機）
**延後**：skip 訊號雜訊未驗證前自動調權會越調越歪；B 完成且 skip 數據證明可信後再評估。

## Recommended Approach：B，分四刀

### 資料模型

```python
@dataclass(frozen=True)
class DJMaterials:          # 純資料，_fetch_dj_interjection_raw 的 IO 段一次收齊
    revival_lines: list[str]
    memory_evidence: str
    focus: str                     # '' / 'song' / 'topic' / 'silent'
    life: list                     # LifeCore | (text, meme_id) | str
    present_members: set[str] | None
    interests: list[str]
    emotional_highlights: list[str]
    news_items: list[str]
    callbacks: list[str]
    activities: list[str]
    has_guide: bool
    has_conversation: bool
    autopilot_reason: str
    exclude_modes: frozenset[str]

@dataclass(frozen=True)
class NarrationMode:
    name: str
    tier: Literal["forced", "gacha", "override"]
    order: int                     # forced/override 層內的先後
    pick: Callable[[DJMaterials, TopicCooldownStore], tuple[str, str|None] | None]
                                   # 回 (topic_text, meme_id) 或 None；只探測、不 mark_used
    weight: float = 1.0            # gacha 層用
    cooldown_s: float | None = None
    render: Callable[[str|None, RenderCtx], list[str]]   # 回要 append 進 ctx 的行
    tts_emotion: str = "normal"
    on_chosen: str | None = None   # 副作用 key（"consume_callback" / "consume_conversation"），由 IO 層執行
    override_when: Callable[[str, DJMaterials], bool] | None = None
                                   # 只給 override 層：收「gacha 層抽中的 mode」+ 素材，回 True 就改用本 mode

@dataclass(frozen=True)
class RenderCtx:                   # render 需要、但不屬於「主素材 topic」的上下文
    env: str                       # atmosphere 用的時間/地點/季節字串
    conv_lines: list[str]          # conversation 用（已過 is_consumed 濾）
    revival_lines: list[str]       # revival 用
    guide: str | None              # guide 用的導聆稿
    song_card: dict | None         # guide 的 gacha motivation / lyric_hook
    empathy_hook: str              # life/interest 的開場鉤子（呼叫端先 random.choice 好，render 保持純）

@dataclass(frozen=True)
class NarrationPlan:
    mode: str
    topic: str | None
    ctx_lines: list[str]
    tts_emotion: str
    side_effects: list[str]
```

`plan_narration(materials, store, rng) -> NarrationPlan` 依序跑 forced 層 → gacha 層 → override 層。

**寫入責任（照抄現行行為，不改語意）：**
- `plan_narration` 自己做的寫入只有 TopicCooldownStore：被選中且有主素材的 mode 呼叫 `mark_used`（news 用 2h 冷卻、memory_match 用預設），gacha 層呼叫 `set_last_fallback(抽中的 gacha mode)`。forced 層命中時**不進** gacha 層，所以 memory_match/revival/song 命中不會碰 life/interest 冷卻（與現行一致）。
- override 層：`reason` 的 `override_when = lambda chosen, m: chosen in ("quick","atmosphere") and bool(m.autopilot_reason)`。override 不呼叫 `mark_used`；`set_last_fallback` 記的是 gacha 抽中的原 mode（quick/atmosphere），不是 reason——與現行 `select_narration_mode` 相同。
- 其餘寫入（conversation `mark_consumed`、callback `consume_callback`）放在 `plan.side_effects`，由 IO 層的 `apply_side_effects(plan, …) -> NarrationPlan` 執行。`apply_side_effects` 是**同步函式（def，不是 async def）**，呼叫端在 `plan_narration` 之後立刻呼叫，中間沒有 await——以函式型別保證 PR #102 的「重查＋標記對 event loop 原子」，並有測試斷言它不是 coroutine function。
- **conversation 降級**：`apply_side_effects` 處理 `consume_conversation` 時先用 `is_consumed` 重查；若全被另一首搶光，回傳 `downgrade(plan, "quick")`（純函式，以 quick 的 render/tts_emotion 重建 plan，topic=None）。呼叫端一律使用 `apply_side_effects` 的回傳值當最終 plan。quick 的 `render` 回 `[]`（quick 的本地模板仍由文字 cascade 處理，與現行降級路徑相同）；降級**不做任何額外冷卻寫入**，`last_fallback` 維持 gacha 抽中的 `conversation`（與現行一致，由第 2 刀的降級斷言鎖住）。

### 分刀（每刀獨立 PR、行為不變的刀先做）

1. **skip 反應訊號 + 刪 prev_song**（行為：只多記錄；prev_song 是零呼叫端死碼，刪除不改任何可觀察行為，所以與記錄併在同一刀）
   - **歸屬**：一段口白歸屬於它**引介的那首歌**（尾段疊播時也是下一首，與現行 `next_info['_dj_played_in_tail']` 同一首）。口白**確定播出**時（`_maybe_play_dj_interjection` / 尾段疊播的 play_tts 成功送進 mixer 之後）才在該首 info 寫 `_narration_id`（uuid）與 `_narration_mode`，並把同一個 id 回寫進 `dj_narration.jsonl`（append 一筆 `{"type":"aired","narration_id":…}`）。生成了但沒播出的（TTS 失敗、被 mute/drop guard 擋、prefetch 取消、退回保底報幕）不寫 id，該首開播歸入基準組。
   - **skip 紀錄**：hook 裝在 `MusicCog._record_song_skip()`（語音 skip 與按鈕 skip 都經過這裡；`clear_music` 不經過，刻意不算——那是清佇列不是表態）。每次被呼叫 append `records/song_skips.jsonl`：`{ts, video_id, elapsed_s, narration_id|null, requested_by}`，`elapsed_s` 以**該首開始播放的時間**為原點（`_current_stream_info` 開播時寫入 `_started_at`）。
   - **開播紀錄**：在寫入 `_started_at` 的同一處 append `records/song_plays.jsonl`：`{ts, video_id, narration_id|null, mode|null, requested_by}`（取自該首 info 的 `_narration_id` / `_narration_mode`；沒播出口白為 null）。每首歌只在**首次開播**寫一筆：resume、重連、mixer 重武裝改寫 `_started_at` 時不重寫（以 info 上的 `_play_logged` 旗標擋）。不沿用 `music_memory.plays[]`，因為它沒有口白欄位。
   - **計算**：分母 = `song_plays.jsonl` 按 mode 分組的開播數（mode=null 為基準組）；分子 = `song_skips.jsonl` 中 `elapsed_s ≤ 30` 且以 `narration_id`（基準組以 `ts`+`video_id` 對應最近一次開播）配回的 skip 數。各 mode skip 率與基準組比較。分析腳本 `scripts/dj_mode_skip_rate.py` 在第 4 刀前寫好。
   - 刪 `prev_song`（select_mode 參數、MODE_WEIGHTS、NON_TOPIC_MODES、orchestrator 參數、相關測試）。
2. **行為護欄**（純測試，對現行程式碼寫、現行就要綠）：沿用 `tests/test_dj_callback.py` 的 harness，固定 rng：
   - **ctx/TTS 快照**：14 個 mode（刪掉 prev_song 後）各一組素材，快照 `generate_dynamic_system_msg` 收到的 ctx 與 TTS 情緒；另加「conversation 抽中但素材被搶光 → quick」降級快照。
   - **冷卻/副作用斷言**：每條路徑（各 forced、gacha 抽中、reason 覆蓋、conversation 降級）跑完後斷言 TopicCooldownStore 內容（哪些 key 被 mark_used、last_fallback 值）與 consume 呼叫；特別斷言 memory_match 命中時 life/interest 的冷卻 key 不存在。
   後面一刀以「快照與斷言全部不變」為驗收。
3. **註冊表 + 規劃器**（行為不變）：新模組 `dj_narration_modes.py`（MODES 表 + plan_narration）；`select_mode` / `select_narration_mode` 改為薄包裝或刪除（呼叫端改用 plan_narration）；`_fetch_dj_interjection_raw` 的 mode 段改成「收 DJMaterials → plan → 套副作用 → ctx.extend(plan.ctx_lines)」；`_DJ_MODE_TO_TTS_EMOTION` 改讀 `MODES[mode].tts_emotion`。`song`（pick_song_facet）、`reason`（song_candidates 拼接）、`quick`（文字 cascade 的本地模板）這三個 mode 的特殊組裝**第 3 刀不搬**，留在原位；其餘 10 個 mode 的 ctx 由 `render` 產生。新模組需在 `main_discord.setup_early_logging` 放行 INFO。驗收：第 2 刀快照與冷卻斷言全綠 + 既有 gacha/orchestrator 測試全綠。
4. **一週後依數據砍 mode**：用第 1 刀的訊號算各 mode skip 率（對照基準組），使用者拍板砍哪些；砍 = 刪一筆 MODES 資料 + 其快照。**開播數 n<20 的 mode 不列入本輪砍除決策**，延長觀察到 n≥20 再評估（前提 3：少見不等於不受歡迎）。

## Open Questions

- `song` mode 的 facet 抽選（pick_song_facet）與 `reason` 的 song_candidates 拼接，要不要也收進 render？第 3 刀先保留在原位，只收「mode 決策 + 主素材 ctx」。
- `quick` 在文字 cascade 裡有特殊路徑（跳 LLM 走本地模板），規劃器只回 mode，cascade 照舊判斷。

## Success Criteria

- 加一個新扭蛋 mode 的**非測試檔**只動 2 個：`dj_narration_modes.py`（MODES 一筆 + DJMaterials 一個欄位）與 `cogs/music_cog_dj_lyrics.py`（收集素材一行）。測試檔需要：一個快照 fixture + 一個「收集接線」測試（真實 vc 成員/素材來源 → DJMaterials 欄位，避免 activity 那種接線漏測）。以「把 activity 重新實作一次」驗證這個數字。
- 第 2 刀的 14 個 mode ctx 快照＋conversation 降級快照，在第 3 刀前後完全一致。
- `_fetch_dj_interjection_raw` statement 數下降（AST 量測）；mode→ctx 的 if/elif 鏈只剩 song / reason / quick 三個分支。
- 第 1 刀上線後一週，每個 mode 有 skip 率數據（n≥20 的 mode）。

### R3-1 — feasibility (blocking)

**Problem**

> The new play-start record takes narration_id/mode from the song info, but _narration_id is stamped when the narration is generated (line 135), not when it is actually heard. A generated narration can fail to air (TTS failure such as edge-tts rate limiting, a play_tts mute/drop guard, prefetch cancelled), or the text cascade can fall through to the 保底報幕, yet song_plays.jsonl would still count that start under the chosen mode. Narrated and non-narrated groups get silently mixed, and because cut 1's week of data is collected before the analysis script exists, this cannot be corrected retroactively. R2-1's remedy explicitly asked to count only narrations that actually played.

**Remedy**

> Stamp narration_id/mode onto the info (or write a played flag into song_plays.jsonl / dj_narration.jsonl) only after the narration TTS was actually enqueued/played, and state that narrations which fell back to the 保底報幕 or failed to air are recorded as null (baseline) or excluded.

### R3-2 — clarity (minor)

**Problem**

> Line 135 only requires writing _narration_id onto the song info; nothing says the narration mode is also written there, so the source of song_plays.jsonl's mode field is undefined. Also unstated is whether re-writing _started_at (e.g. resume after reconnect) produces duplicate play-start rows.

**Remedy**

> State that narration generation writes both _narration_id and _narration_mode onto the info, and that song_plays.jsonl is appended once per song start (not on resume/re-arm).
