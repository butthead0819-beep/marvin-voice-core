# Marvin 核心規範

狀態：**v1**（2026-10-26，原則原文由 Jack 訂定；§6 四題已拍板；標 ⬜ 處的數字仍是草案，等第一次週審有資料再定）

這份文件有三個用途：
1. **設計原則**——任何新功能、改動，開工前先對照七條原則（§3 設計審查清單）
2. **量測定義**——每條原則對應可機器判斷的指標，寫明資料源與門檻
3. **定時審查**——每週/每月照 §4 跑一遍，指標壞了照「調整方向」處理

---

## 1. 七條原則（原文）

1. 是一個能記憶生活與喜好的 agent
2. 從使用者的記憶中產生選擇與陪伴
3. 使用者一直跟別人說話時，可以維持現狀不打擾
4. 使用者有需求時會喚醒並等待回覆，這時候就要越快越好
5. 不確定時就不要接需求
6. 聲音是介面，也是打擾行為，聲音很大或很長就是要小心謹慎
7. 獲取使用者的注意力，就是要期待使用者滿意

**一句話**：Marvin 平常是房間裡安靜的空氣，靠記憶選歌陪伴；被叫才開口，開口就要快、要短、要讓人滿意；沒把握就閉嘴。

### 原則衝突時的優先序 ⬜

| 順位 | 原則 | 理由 |
|---|---|---|
| 1 | 5 不確定不接、6 聲音謹慎、3 不打擾 | 「守門」類：做錯的代價（打擾、誤觸發）大於少做的代價 |
| 2 | 4 喚醒要快 | 已確定有需求時，速度是第一體驗 |
| 3 | 7 注意力要換到滿意 | 主動發話的准入條件 |
| 4 | 1 記憶、2 從記憶產生選擇 | 底層能力，透過其他原則表現出來 |

例：「為了快（4）跳過確認」若會提高誤接率（5），不做。「記得一件事（1）想主動講（2）」但房間正在熱聊（3），不講。

## 2. 逐條：意思、守則、量測、調整

每條的「狀態」：✅ 現在就能量／🟡 部分能量／🔴 量測點不存在或已斷。

### 原則 1：能記憶生活與喜好

**意思**：記得每個人的喜好（歌、歌手、遊戲）和生活事件（說過的事、近況），而且記得**準**。

**守則**
- 只記使用者說過、做過的事；不准 LLM 推測出「事實」寫進記憶（見 feedback_no_llm_invented_facts）
- 記錯比沒記更糟：有糾正管道（勘誤 agent、刪 taste 要同步清 likes）
- 記憶有生命週期（30 天衰減），不是只進不出
- 真人點某位歌手的歌＝強化點歌者口味裡既有的這位歌手（+0.5，每項 24h 一次；10/26 拍板）。常聽的不該被衰減淘汰
- **現場確認**（10/26 拍板）：房間沉默夠久時，換歌空檔用一句「X，你還喜歡 Y 嗎？」取代那次 DJ 口白；只問口味（歌手、遊戲、食物；分類不出來就不問）、輪流問在場者、多人在場也可；只收被問者 15 秒內的回答，對＝強化、不對＝刪除、聽不懂＝不改

**量測**

| 指標 | 資料源 | 現況（截至 10/26） | 門檻 |
|---|---|---|---|
| 記憶抽查正確率 | `records/quality_metrics.jsonl` metric=`recall`（人工確認） | 10 月 105 筆 | ≥ 90% ⬜ |
| 現場確認正確率 | `records/memory_checks.jsonl`（答「對」÷ 有明確回答） | 🔴 待上線 | ≥ 90% ⬜ |
| 記憶被糾正次數/週 | 勘誤 agent 觸發、「不是啦／我沒說過」 | 🔴 沒有統一計數 | 週趨勢不上升 |
| 新記憶產出/週 | daily review delta 輸出 | ✅ 有 | 有人在房間的週 > 0 |

**調整方向**：正確率低 → 先查是 STT 糊字進記憶、還是萃取 prompt 張冠李戴；產出為 0 → 查 daily review 有沒有跑（盯產物不盯 log）。

**狀態**：🟡

### 原則 2：從使用者的記憶中產生選擇與陪伴

**意思**：選歌、DJ 口白、關心追問，素材都來自「這群人的記憶」，而不是泛用推薦。

**守則**
- **Marvin 關注在場的人**（10/26 拍板）：選擇的種子來自在場成員的共同喜好；不在場的人的記憶不拿來當種子
- 發現新歌（discovery）只要種子來自在場成員的記憶，就算「從記憶產生」；拿排行榜等外部來源當種子的不算
- 「共同」＝輪流照顧每位在場者（10/26 拍板，即現行 T2 做法）
- 推薦掛名照實（`recommend_attribution()`），不冒充某人點的
- 隱私：某人的記憶只在本人在場時用；情緒事件只內化不唸出

**量測**

| 指標 | 資料源 | 現況（近 7 天） | 門檻 |
|---|---|---|---|
| Marvin 推薦歌 skip 率 | `song_plays` × `song_skips`，requested_by 含「Marvin」 | 35 / 1222 = **2.9%** | ≤ 5% |
| 選歌來自在場者記憶的比例 | `agent_recommendations.jsonl` 的 `lane`；⬜ 需把 discovery 拆成 T2（在場者種子）/T4（含排行榜） | 近 14 天 discovery 78%，但 T2/T4 分不開 → 目前算不出 | ≥ 50% ⬜ |
| 人工點歌 skip 率（對照組） | 同上，非 Marvin | 7 / 43 | 只看趨勢 |

**調整方向**：skip 率升 → 依 lane 拆，看是哪一層候選池出問題（skip 調推薦邏輯，不 blacklist 歌）；記憶比例過低 → 查 T1 候選是否被排除規則吃光。

**狀態**：✅

### 原則 3：使用者一直跟別人說話時，維持現狀不打擾

**意思**：房間在聊天時，Marvin 是背景。不插話、不主動發話、不做會引起注意的改變。

**守則**
- 熱聊時**允許**：歌播完照常接下一首、Active Music Balance 自動壓低音樂（10/26 拍板）
- 熱聊時**不允許**：任何出聲——DJ 口白（含 ≤5 秒短版）、追問、漫才、主動話題，一律不講（不是延後到熱聊中途插進來）
- 窗外有人講話：不切 Marvin 的話，只 duck（已實作）
- 多人熱聊＝靜音陪伴

**量測**

| 指標 | 資料源 | 現況 | 門檻 |
|---|---|---|---|
| 熱聊期間「非請求」TTS 次數（含 DJ 口白） | 需要：每次 TTS 記 kind + 當下熱度 | 🔴 沒有這個 log | **0** |
| 主動發話 bid 被熱度擋下的比例 | `speak_outcomes.jsonl`（`present_speakers`、`silence_seconds`、`tts_pushed`） | 7 天 16 bid / 7 出聲 | 只看趨勢 |
| 打斷他人講話次數 | `quality_metrics` metric=`interruption` | 🔴 **6 月後停止寫入** | 0 |

**調整方向**：非請求 TTS 在熱聊出現 → 找出那個 SpeakKind，把它加進熱聊擋門，不是調熱度門檻。

**狀態**：🔴（關鍵 log 缺，見 §5）

### 原則 4：有需求時喚醒並等待回覆，越快越好

**意思**：喊「馬文」之後，到聽到 Marvin 第一個聲音（ack 或答案）的時間越短越好；對談窗內等使用者把話講完。

**守則**
- 延遲優化先量後改（E1 打點），不憑推測
- 先給聲音（ack / 確認句）再給答案，但 ack 也受原則 6 約束（要短）
- 對談窗內只有提問者能打斷 Marvin

**量測**

| 指標 | 資料源 | 現況（近 7 天） | 門檻 |
|---|---|---|---|
| 喚醒→回應延遲 p50 / p90 | `response_feedback.jsonl` `wake_latency_sec` | n=40，**p50 6.9s / p90 13.9s** | 階段一：**p50 ≤ 5s**（10/26 拍板）；達標後再訂下一階段 |
| 停話→intent 派發 | `pipeline_timing.jsonl` `total_ms` | ✅ 有 | 只看趨勢，拆瓶頸用 |
| 喚醒漏接率 | 代理：短時間內連喊兩次以上「馬文」 | 🔴 沒有統計 | ≤ 5% ⬜ |

**調整方向**：延遲壞 → `scripts/analyze_latency_breakdown.py` 拆段，砍最大段；漏接升 → 先查 STT 層（喚醒漏接三道防線），不是放寬意圖門檻（會違反原則 5）。

**狀態**：🟡（延遲 ✅、漏接 🔴）

---

### 原則 5：不確定時就不要接需求

**意思**：誤接（沒人叫卻回應、聽錯指令照做）的傷害大於漏接。沒把握就不動作。

**守則**
- 指令一律要喚醒詞（含窗內）；窗內無喚醒詞只准唯讀 agent
- 信心不足：**不執行、完全不出聲**——不反問、不給提示音（10/26 拍板）
- 寧可讓使用者再叫一次，也不要做錯一件事

**量測**

| 指標 | 資料源 | 現況 | 門檻 |
|---|---|---|---|
| 誤回應率 | `quality_metrics` metric=`false_responding` | 🔴 **6 月後停止寫入** | ≤ 5% ⬜ |
| 執行後被糾正/撤銷 | `turn_outcomes.jsonl` `corrected` | 🔴 欄位存在但 104 筆全是 null（沒接） | ≤ 5% ⬜ |
| TurnGate 擋下 vs 放行 | `turn_gate_decisions.jsonl` | ✅ 有 | 只看趨勢 |

**調整方向**：誤接升 → 收緊那條放行路徑的門檻；同時看原則 4 的漏接率，兩者一起看才知道是取捨還是 bug。

**狀態**：🔴

---

### 原則 6：聲音是介面也是打擾，大聲或很長要謹慎

**意思**：Marvin 每一秒的聲音都在花使用者的注意力。越大聲、越長，越需要理由。

**守則**
- 所有 TTS 統一 -14 LUFS，不准 per-kind 加大
- 主動發話（DJ 口白等）≤ 5 秒；被要求的回答 ≤ 15 秒，除非使用者明確要長答 ⬜
- 緊急停止（「馬文閉嘴」）永遠有效
- 不疊播：filler、確認句、答案不在同一時間疊起來

**量測**

| 指標 | 資料源 | 現況 | 門檻 |
|---|---|---|---|
| TTS 長度分佈（依 kind） | 需要：每次播出記 kind + 秒數 | 🔴 沒有統一 log | 主動 p95 ≤ 5s、回答 p95 ≤ 15s ⬜ |
| 每小時主動發聲總秒數 | 同上 | 🔴 | ≤ 60 秒/小時 ⬜ |
| 緊急停止觸發次數 | estop log | ✅ 新上線 | 每次都要查原因 |

**調整方向**：長度超標 → 找 kind，砍 prompt 字數上限或改分段；estop 觸發 → 當作 P1 事件回放前 2 分鐘。

**狀態**：🔴

---

### 原則 7：獲取注意力，就要期待使用者滿意

**意思**：Marvin 每次主動開口（不是被叫）都是在借使用者的注意力，借了就要還「滿意」。沒把握讓人滿意就別開口。

**守則**
- 主動發話要能說出「這句話讓誰滿意」，說不出來就不講
- 負面反應（閉嘴、打斷、「吵死了」、講完馬上 skip）＝ 這類發話要減量
- 「滿意」的定義（10/26 拍板）：
  - **正面**：接話、笑、點名回應、說好/讚
  - **負面**：閉嘴/estop、打斷、「吵死了」類、講完 30 秒內 skip
  - **沒反應＝中性，不計分**——不算好也不算壞

**量測**

| 指標 | 資料源 | 現況（近 7 天） | 門檻 |
|---|---|---|---|
| 負面率＝負面次數 ÷ 主動發話總數 | 需要：主動 TTS 後 30s 內的反應分類 | 🔴 | ≤ 10% ⬜ |
| 正面率＝正面次數 ÷ 主動發話總數 | 同上 | 🔴 | 只看趨勢 |
| 現有 `response_feedback` | `reaction_type` | 40 筆中 22 筆「抽樣跳過，預設正常」、17 筆「20 秒無反應」標「嚴重」 | **不可信，不拿來判斷** |
| `turn_outcomes.satisfaction_signal` | — | 104 筆全 null | 🔴 沒接 |

**調整方向**：負面率升 → 依 SpeakKind 拆，砍負面率最高的那一類（先問該不該存在，再問怎麼改好）。

**狀態**：🔴（定義已定，量測點待補 G1/G3）

## 3. 設計審查清單（新功能／改動開工前）

改到「Marvin 會出聲、會做事、會記東西」的地方，開工前逐條回答。任何一題答不出來就先停下來問 Jack。

1. **記憶**：這個功能讀/寫了誰的記憶？寫入的是使用者說過的事，還是 LLM 推測？
2. **選擇來源**：選擇（歌、話題、回應）是從這群人的記憶來的嗎？
3. **熱聊**：房間正在熱聊時，這個功能會做什麼？（答案應該是「不出聲」或「延後」）
4. **延遲**：如果在喚醒路徑上，加了多少毫秒？有量嗎？
5. **不確定**：信心不足時這個功能會怎樣？會不會「猜一個」？
6. **聲音**：會出聲嗎？最長幾秒？受不受 estop / 統一響度管？
7. **滿意**：這是主動發話嗎？怎麼知道使用者滿不滿意？有記下來嗎？

順帶檢查：這個功能該不該存在（先列「拔掉」選項）。

## 4. 定時審查

### 每週（⬜ 週一，跟每日起手儀式一起跑）

逐條看 §2 的指標表，填這張表：

| 原則 | 本週數字 | 上週 | 是否過門檻 | 動作 |
|---|---|---|---|---|
| 1 記憶正確率 | | | | |
| 2 推薦 skip 率 / 記憶比例 | | | | |
| 3 熱聊非請求 TTS | | | | |
| 4 喚醒延遲 p50/p90 | | | | |
| 5 誤回應率 | | | | |
| 6 主動發聲秒數/小時 | | | | |
| 7 主動發話負面率 | | | | |

規則：
- **過門檻**：不動
- **沒過門檻**：開一個 todo，照該條「調整方向」處理
- **連續兩週沒資料**：量測壞了，修量測優先於修功能
- 有人在房間的時數太少（樣本不夠）時，該週標「樣本不足」，不下結論

### 每月

- 檢查門檻本身合不合理（太鬆 = 一直綠但體感差；太緊 = 一直紅但沒人抱怨）
- 回顧當月新功能有沒有走過 §3 清單
- 對照北極星（房間有人時數）看整體趨勢
